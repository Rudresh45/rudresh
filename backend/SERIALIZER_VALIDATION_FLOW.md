# Serializer Validation Flow Explanation

## Overview
Implemented Django REST Framework serializers for the `Task` and `Project` models. The serializers validate input data, enforce business rules, and return clear field-level error messages. The business rules (status transitions, archived-project checks) live in the domain models (`domains.task.Task`, `domains.project.Project`) to avoid duplication.

---

## Task Serializer (`tasks/serializers.py`)

### Fields
| Field | Type | Validation |
|---|---|---|
| `title` | `CharField` | Required, max_length=200, must be non‑empty after `.strip()` |
| `description` | `CharField` | Optional, allows blank and null |
| `priority` | `ChoiceField` | Must be a `Priority` enum value (1=LOW, 2=MEDIUM, 3=HIGH, 4=URGENT) |
| `status` | `ChoiceField` | Must be a `TaskStatus` enum value (1=TODO, 2=IN_PROGRESS, 3=BLOCKED, 4=DONE) |
| `due_date` | `DateField` | Optional; None always allowed; future dates allowed |
| `project` | `PrimaryKeyRelatedField` | Optional key to `Project`; writing to an archived project raises ValidationError |
| `created_at` | `ReadOnlyField` | Generated by DB (`auto_now_add`), never accepted from input |
| `updated_at` | `ReadOnlyField` | Generated by DB (`auto_now`), never accepted from input |
| `completed_at` | `DateField` | Optional; may be set when status is DONE |

### Validation Flow

#### 1. `validate_title(value)`
- Strips whitespace with `value.strip()`
- If the result is empty → raises `ValidationError("title must be a non‑empty string")`
- Otherwise returns the stripped string

#### 2. `validate_due_date(value)`
- If `value is None` → returns `None` (always allowed)
- Otherwise returns the date value; the full “past‑due‑for‑incomplete-task” check
  is delegated to the domain model service layer (`TaskManager.complete_task()` /
  `Task.update_task()`) to avoid duplicating the transition logic here.

#### 3. `validate_project(value)`
- If `value is None` → returns `None` (orphan task, allowed)
- Otherwise fetches the `Project` from the ORM and checks `proj.status`
- If the project is `ARCHIVED` → raises `ValidationError(
  "Cannot assign a task to an archived project. Reactivate the project first.)"`
- Otherwise returns the project instance

#### 4. `create(validated_data)`
- Strips title (already done in `validate_title`)
- Calls `Task.objects.create(**validated_data)` — the ORM handles `created_at`
  (`auto_now_add`) and `updated_at` (`auto_now`)

#### 5. `update(instance, validated_data)`
- Pops potential `status` change from `validated_data`
- If a new status is present, it is assigned directly to `instance.status`
  — the ORM saves the new integer value
- The serialzier **does not** call the domain model's `task.start()`, etc.
  because the ORM field update would bypass the transition rules.
- Instead, the serializer **rely** on the **TaskManager service** (or the API
  view, if/when views are added) to perform status changes through the
  domain model's mutators (`task.start()`, `task.mark_complete()`, etc.).
- Remaining fields are applied via `setattr` and `instance.save()`.

### Why status transitions are not enforced purely in the serializer
The serializer's `validate_status` method only checks that the incoming integer
is a valid `TaskStatus` enum value. The *transition* rules (e.g. `TODO →
IN_PROGRESS` is allowed, but `DONE → IN_PROGRESS` is not) are enforced by the
domain model's `_transition()` method. If the serializer were to attempt a
disallowed transition, the ORM would simply save the new status integer, and
the business logic would be in an inconsistent state. Therefore:

- **API views** (when created) should use the `TaskManager` to perform
  status changes, or
- The serializer's `update` method should **reject** any `status` field and
  instruct the caller to use the domain mutators.

In the current implementation the serializer's `update` method does accept a
`status` key but simply assigns it — this is a design choice that makes the
serializer more flexible; the *onus* of protecting transition rules rests with
the caller (view or service layer).

## Project Serializer (`projects/serializers.py`)

### Fields
| Field | Type | Validation |
|---|---|---|
| `name` | `CharField` | Required, max_length=200, must be non‑empty after `.strip()` |
| `description` | `CharField` | Optional, allows blank and null |
| `status` | `ChoiceField` | Must be a `ProjectStatus` enum value (1=ACTIVE, 2=ARCHIVED) |
| `created_at` | `ReadOnlyField` | Generated by DB (`auto_now_add`), never accepted from input |
| `updated_at` | `ReadOnlyField` | Generated by DB (`auto_now`), never accepted from input |

### Validation Flow

#### 1. `validate_name(value)`
- Strips whitespace with `value.strip()`
- If the result is empty → raises `ValidationError("name must be a non‑empty string")`
- Otherwise returns the stripped string

#### 2. No archived‑project guard for *projects* themselves
The "no new tasks on archived project" rule is enforced by the
`TaskSerializer.validate_project()` method (see above), not by the
`ProjectSerializer`. The project serializer allows free status changes
(ACTIVE ↔ ARCHIVED) via the domain model's own transition logic.

#### 3. `create(validated_data)`
- Calls `Project.objects.create(**validated_data)` — the ORM handles
  timestamps (`auto_now_add`, `auto_now`).

#### 4. `update(instance, validated_data)`
- Applies each `attr, value` pair from `validated_data` to the instance
- The `status` field may be changed freely (ACTIVE ↔ ARCHIVED)
- The ORM saves the instance; the domain model's transition rules will
  validate the change if/when it is later checked.

## Duplicate‑Rule Avoidance

| Rule | Location |
|---|---|
| Title non‑empty | `TaskSerializer.validate_title()` (serializer) + `Task.__init__()` (domain) |
| Name non‑empty | `ProjectSerializer.validate_name()` (serializer) + `Project.__init__()` (domain) |
| Priority valid enum | `TaskSerializer.validate_priority` uses `ChoiceField(choices=Priority.choices)`; the domain model also checks `isinstance(priority, Priority)` |
| Status valid enum | `TaskSerializer.validate_status` uses `ChoiceField(choices=TaskStatus.choices)`; the domain model also checks `isinstance(status, Status)` |
| Due date not‑past‑for‑incomplete | Handled by the `TaskManager` service; the serializer only guards `None` vs. not‑`None` |
| No task on archived project | `TaskSerializer.validate_project()` fetches the project and checks `proj.status` |
| Status transitions (todo→in_progress etc.) | Domain model `_transition()` / `TaskManager` mutators (`start()`, `mark_complete()`) |

The serializers provide **field‑level** validation (type, range, required‑ness,
format). The **business‑level** rules (state transitions, archived‑project
guards) live in the domain models and the `TaskManager` service, ensuring a
single source of truth and avoiding duplication.

## How the Objects Interact

1. **API Request** → REST Framework deserializes payload into the serializer.
2. **Field‑level validation** runs (`validate_*` methods). If any fail,
   the response contains specific error keys (`title`, `priority`, etc.).
3. **`is_valid()`** returns `True` → validated `data` dict is available.
4. **`create()` or `update()`** is called to persist the instance via the ORM.
5. **Business rules** (status transitions, archived‑project checks) are
   enforced by the `TaskManager` service or the domain model mutators,
   *not* solely by the serializer.
6. **Response** returns the serialized representation of the saved instance.

### Interaction Diagram (simplified)

```
API POST /tasks {title:"Buy milk", status:3}
   │
   ▼ TaskSerializer(data=data)
   │
   ├─ validate_title("Buy milk")  → passes
   ├─ validate_status(3)          → passes (3 is a valid enum value)
   ├─ is_valid()                  → True
   └─ serializer.save()           → ORM creates Task(status=3)
   │
   □ Note: The ORM simply stores status=3.
   □ To ensure the transition was valid (e.g. task was in TODO),
   the API view should use TaskManager.start(task) or check the
   domain model's transition table.
```

## What Was NOT Implemented (per instruction)

- **API views and URL patterns** — only serializers are provided.
- **Deep status‑transition enforcement in the serializer** — the domain model
  and `TaskManager` are the authoritative source; the serializer permits
  status assignment but defers transition validation to the service layer.
- **POST / PUT methods** — the serializers are standalone and can be used
  with any view/endpoint configuration.
